# Decisions (engineering)

Product decisions live in `docs/PRODUCT_DECISIONS.md`. This file records engineering decisions made while executing the platform directive (2026-10-15).

| # | Decision | Why | Reversible? |
|---|---|---|---|
| E1 | **No rename to "ORIAN".** Code, routes, cookies and docs stay `ORYN`. | The founders chose the "symbol + ORYN" wordmark on 2026-09-30; "ORIAN" is the spelling on the logo file. Same product. Renaming a working codebase on a spelling difference would be destructive and was explicitly ruled out by the directive ("never rename based on an assumption"). | Yes — a rename is a find-and-replace plus cookie names, once the founders decide. |
| E2 | **Keep the existing stack**: Next.js 15 + TypeScript + Tailwind, raw SQL on PostgreSQL (PGlite for local/tests), Postgres-backed job queue, Vitest + Playwright. **Not** adopting Prisma, Redis or BullMQ. | Every working module (auth, cards, Nearby, People, stations, events, privacy) is built on this. A rewrite to Prisma would touch all of it for no user-visible gain; Redis/BullMQ add infrastructure to own. The founders' standing rule: no unnecessary vendors, don't destructively change working code. The job queue already has retries, backoff and `SKIP LOCKED`. | Yes, module by module. |
| E3 | **Keep own authentication** (scrypt via Node's `crypto`, hashed session tokens, HttpOnly cookies, per-account lockout). Added email verification and password reset on top, using the same hashed-token pattern. | The directive says "use established libraries, never custom password cryptography". The hashing *is* the standard library primitive (scrypt, RFC 7914); there is no home-made cipher. Swapping to an auth framework would re-implement what already passed the security test report. | Yes. |
| E4 | **Email via an outbox table + pluggable transport.** `EMAIL_TRANSPORT=smtp` uses the company's own SMTP server (no email SaaS); `log` (default outside production) prints to the server log; unset in production = emails are recorded as `skipped`, never silently lost. | Transactional email is required for verification, reset, tickets and automations; the founders don't want a paid provider. SMTP is a protocol, not a vendor. | Yes — add a transport. |
| E5 | **Registrations and tickets are one table.** A ticket is the registration's signed token; its QR encodes `/ticket/<token>`. Check-in is an atomic `UPDATE … WHERE checked_in_at IS NULL`. | One row per attendee avoids drift between "registration" and "ticket" and makes duplicate entry impossible by construction. | Yes. |
| E6 | **Leads (CRM) live in the workspace**, not on the personal account; People stays personal. A lead can link to a station, an event and an assignee. | Tenant isolation: workspace data is governed by workspace roles; personal relationship memory stays private to the person. | Yes. |
| E7 | **Automations run through the existing job queue** with an idempotency key per (automation, subject). | Retries, backoff and failure logging already exist there. | Yes. |
| E8 | **AI is a provider interface with explicit consent and a non-AI fallback.** Nothing leaves the server unless `ORYN_AI_PROVIDER` is set *and* the user has turned on "AI assistance" in settings. | Directive §23 and the founders' privacy stance. | Yes. |
| E9 | **Stations get a `mode`** (card · lead capture · event registration · check-in · booking · link) and one HTTPS URL that serves NFC and QR alike; `/s/<code>` is an alias of the existing `/q/<code>`. External destinations must be `https://` and are validated server-side. | Directive §11–12, without breaking printed codes already in use. | Yes. |
| E10 | **Paid ticketing and billing stay behind the existing simulated provider.** Free events work end to end; "paid" ticket types are stored but cannot be sold until a payment provider is configured. | No approved payment provider yet. | Yes. |
| E11 | **Branding is configuration, not a rename.** `NEXT_PUBLIC_BRAND_NAME` sets the product name everywhere a person sees it (shell, entry, manifest, emails via `BRAND`); the logo switches to a text wordmark for a non-default name. Identifiers (`oryn_*` cookies, `ORYN_*` env, routes, tables) stay. | Genesis V2 asked to "verify ORYN and ORIAN are the same product before renaming" — they are the same product (E1). A config switch lets the founders show "ORIAN" today with zero destructive change. | Yes — set the variable. |
| E12 | **Apple Wallet signing is first-party via OpenSSL** (`lib/server/wallet-pkpass.ts`), not a pass-generation service. Unsigned archives exist only as clearly labelled development previews. | No vendors; Apple's format is a ZIP + SHA-1 manifest + PKCS#7 signature, which OpenSSL produces. Node has no CMS signer in its standard library. | Yes — swap `signManifest` for a library when one is approved. |
| E13 | **Realtime = Server-Sent Events over the existing database** (`/api/v1/stream`, 1.5 s server watch, change-only emits), with polling kept as the fallback. No WebSocket server, no Redis pub/sub. | One stateless HTTP endpoint works on every host the stack targets, reconnects for free with `EventSource`, and needs no new infrastructure. Upgrade path: replace the watcher with `LISTEN/NOTIFY` when the deployment runs on a dedicated PostgreSQL. | Yes. |
| E14 | **Production builds never print sign-in hints.** The local-demo credentials note on `/signin` appears only when `NODE_ENV !== 'production'`. | Security audit item in Genesis V2; demo data in production is itself alerted in Command Center. | — |
| E15 | **Ticket states are derived, not stored**: Valid · Checked in · Cancelled · Expired (event ended, never used) · Waitlisted, computed on the ticket page from `status`, `checked_in_at` and the event's end time. | No background job can drift; the door still refuses a used ticket atomically. | Yes. |
